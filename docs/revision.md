# 局部修改：按要求改，而且不把已经满意的部分改坏

第一次成片之后，竞争点就不在「能不能自动做」了。真实的下一句话长这样：

> 第三个镜头保持人物表情和场景不变，相机再向右移动一点；不要变焦，前景遮挡保留；第四个镜头要接得上。

这一句里藏着五个必须分别解决的问题。下面逐个说现在做到了什么、靠什么机制、以及还差什么。

---

## 1. 系统是否保存了可编辑的场景、相机和时间线状态？

**是。这是这套东西从第一天起的前提，不是后加的。**

`core/store.js` 是 Source of Truth：实体（语义类型 / 位置 / 姿态 / 关节 / 连续性）、机位（pose / lens / rig）、灯光（含强度关键帧）、镜头（入出点 / 运镜 / 关键帧 / 目标）、走位路径、故事版、Take、生成任务，全是结构化数据，`persistable()` 出来就是一份完整工程 JSON。

生成结果**不是**这份状态的替代品，而是它的一次渲染。所以「重做第三镜」永远有东西可依据——不是拿着一段视频去 img2img 碰运气。

| | 只有视频文件 | 有可编辑状态 |
|---|---|---|
| 「机位右移 15 cm」 | 只能靠提示词描述，模型自己理解 | 真的把机位挪 0.15 m，重编译提示词 |
| 「第四镜要接得上」 | 靠人眼比对 | 第三镜出点的机位/实体状态是算出来的 |
| 「撤回上一次修改」 | 没有 | `project.undo` / `undo-to <eventId>` |

---

## 2. 「向右移动一点」对应哪个坐标系、多少距离？

**做了 `camera.nudge`，把这句话变成一个确定的数。**

```bash
director camera.nudge --id cam_program --direction right --amount 一点
→ 右移 0.15 m（机位坐标系，焦段与视线目标不变）
```

三件事被钉死了：

- **坐标系**：机位自身。`right` = 画面右方、`up` = 画面上方、`forward` = 朝向被摄体。由「位置 → look-at 目标」这条视线算出正交基，不是世界坐标的 X 轴——否则机位转过身之后「向右」就反了。
- **距离**：`一点点 0.08 / 一点 0.15 / 一些 0.4 / 明显 1.0 / 大幅 2.0`（米）。想精确就直接给米数。词表写在 `NUDGE_STEPS`，可以按项目调。
- **它是平移不是摇镜**：移动后 `lookAt` 保持原来那个点，焦段一个字不改。这正是下一个问题的关键。

结果会原样说出来（`describe` 字段），事件日志里留着 `from` / `to`，所以「刚才到底挪了多少」永远查得到。

---

## 3. 视频模型有没有把横移变成摇镜或者缩放？

这是最容易翻车的一条，分两头处理。

**事前**：`camera.nudge` 会在镜头上记一条 `lastMove`，提示词编译器把它写成一句没有歧义的机位指令，并把**没要改的维度显式钉死**：

> 本次机位变化：横移右 0.15 米。只做平移，机身保持与原轴平行，主体构图不变，焦段固定 40mm。不要摇镜、不要俯仰、不要变焦、不要滚转、不要滑动变焦。

negative 里同时加上 `pan, tilt, zoom, roll, dolly zoom, handheld shake`。正负两头都写，因为生成模型对否定式并不可靠，只给 negative 拦不住。

**事后**：`review.verify` 让多模态模型专门判一次 `cameraMove`，判定尺度写进了系统提示词：

> 主体在画面里横向位移、而背景透视关系跟着变，是 truck；主体位置不动而背景横扫过去，是 pan；主体变大变小是 zoom 或 dolly。这一条最容易错，看不准就写 unclear。

看不准就说看不准，比硬给一个答案有用。

## 4. 重新生成后，人物身份、动作和光线是否漂移？

**两道防线：一致性参考（事前）+ 自动验收（事后）。**

事前已有的：角色/产品先 `generation.reference` 出定妆照 → `asset.approve` → 之后该实体出现的每个镜头自动带上参考图。参考绑在**实体**上不绑在镜头上，所以导演批准一次就够。（MAISON 那次 10 个任务每个都带了 4 张参考。）

事前新增的：`shot.lock`（见第 5 条）把「已经满意的部分」编进提示词的正向约束。

事后新增的：`review.verify` 抽新旧两版各 3 帧（首/中/尾）交给多模态模型逐项对比，返回结构化结论：

```json
{"applied": false, "appliedNote": "没有执行平移机位的指令…",
 "cameraMove": "unclear", "worst": "major",
 "drift": [{"aspect":"framing","changed":true,"severity":"major","note":"景别从大远景突变为中特写…"},
           {"aspect":"identity","changed":true,"severity":"major","note":"白色方形包变成黑色手提包…"}],
 "summary": "严重漂移，变成了完全不相关的镜头，必须重新生成。"}
```

**为什么不做像素差**：生成视频每一帧都是重画的，像素差分不出「机位右移 15 cm」和「换了一个人」，两者的数值可能一样大。

**判定结果只是建议**：它写进 `shot.lastVerdict`，不自动通过也不自动打回。生成模型会错，判定模型同样会错，拍板的是导演。

实测（两个真实片段）：同一条片子自比 → `worst: none`，三项全部 `changed: false`；两条不同镜头 → `worst: major`，framing / identity / lighting 全部命中，并正确指出「要改的那件事没做」。能区分，不是一律报警。

## 5. 能否只重做一个镜头，并继续满足前后镜头的连续性？

**单镜重做**：一直可以——`generation.submit {shotId}` 就是逐镜的，`film.export {source:"auto"}` 会把这一镜的新结果换进成片、其余不动。

**别把满意的改坏**：这是新加的 `shot.lock`。

```bash
director shot.lock --shotId shot_03 --aspects identity,performance,lighting,foreground,lens
```

九个可锁的维度：`identity 人物身份 / wardrobe 服装造型 / performance 表演动作 / framing 构图取景 / lighting 灯光 / palette 色彩 / background 背景环境 / foreground 前景遮挡 / lens 焦段光圈`。每一项都带三样东西：编进提示词的正向说法、负向说法、以及**哪些 Action 会动到它**。

锁生效在 `dispatch` 这一层，不是在每个 handler 里——所以界面、CLI、Agent、curl 全都拦得住，没有漏网入口：

```
light.update  → LOCKED  shot_03「…」锁了灯光。要改就先 shot.unlock，或带 force 越过（会记进事件日志）。
```

拦截范围按 aspect 的性质定，避免误伤：灯光/色彩/背景是**全场**的（任何改动都落在每个镜头上）；身份/服装/表演只在**这一镜的被摄主体**上；构图/焦段只在**这一镜的机位**上。所以锁了第三镜不会挡住你改第四镜的机位。

`force` 能越过，但事件日志会记 `forced: ["shot_03:lighting"]`——事后查得到是谁越过的、越过了什么。

**前后接得上**：目前靠两件事——`context.sequence` 给出整条时间布局，`cameraStateAt(shot, outFrame)` 能算出第三镜出点的机位与实体状态，用来编译第四镜的入点。**还没做的**是把它固化成一个显式约束（`shot.continuity {from, to}`，让第四镜的首帧直接用第三镜的尾帧做 i2v 锚点）。这是下一步，见文末。

## 6. 同一份镜头要求，各种控制方式各自能保留多少约束？

按「能锁住什么」从弱到强：

| 控制方式 | 能保留的约束 | 保不住的 | 代价 |
|---|---|---|---|
| **纯文本** | 语义：谁、在哪、什么景别、什么光 | 精确构图、身份、运动曲线。每次重跑都重新掷骰子 | 最低 |
| **文本 + 参考图**（已有） | 上面 + 身份 / 产品外观 / 材质 | 构图与运动 | 低，一次出图 |
| **首帧 i2v**（已有） | 上面 + 起幅构图基本锁死 | 运动方式；而且**首帧会压过参考图**——MAISON 那次手袋颜色漂移就是这么来的：白模关键帧里展台是象牙白，压过了参考图里的黑色 | 低 |
| **白模视频 v2v**（已有，需公网） | 上面 + 运动矢量、时序、机位轨迹 | 材质与光照细节 | 中，要先录白模 |
| **深度 / 光流 / 轨迹**（未做） | 上面 + 几何与遮挡关系逐帧对齐 | 风格 | 高，要额外通道 |
| **补训练 / LoRA**（未做） | 身份与风格跨镜头稳定 | 单镜构图 | 最高，要数据与训练 |

**首帧与参考图会打架**这件事已经在适配器里处理了：有已批准参考时跳过故事版首帧，让身份优先（`ark.mjs` 里那段注释）。代价是起幅构图松一点。哪个优先应该是导演的选择，目前是写死的——该做成 `shot.lock` 的一个开关。

## 7. 失败之后，换提示词、换控制输入、还是补训练数据？

`review.verify` 的输出正好对应这三条路，按现象分诊：

| 验收结论 | 说明什么 | 该动哪一层 |
|---|---|---|
| `applied: false`，锁的都没漂 | 模型没理解这次的要求 | **换提示词**：把要求写得更具体（`camera.nudge` 已经在做这件事） |
| `applied: true`，但 `cameraMove` 不对（要 truck 给了 pan） | 文本约束不住运动 | **换控制输入**：上白模 v2v，用运动矢量锁住轨迹 |
| `drift` 里 identity / wardrobe 是 major | 参考图不够强，或被首帧压过 | **换控制输入**：多给几张参考、或改用 t2v + 参考图放弃首帧 |
| 反复多轮之后同一个人还是稳不住 | 这个身份超出了模型的泛化范围 | **补训练数据**：为这个角色做 LoRA |
| `drift` 是 lighting / palette 的 major | 场景语义没传到位 | 先**换提示词**（灯光组已经在编译里，检查是不是被风格描述压过） |

顺序上先便宜的：提示词 → 控制输入 → 训练。补训练数据是最后一格，因为它最贵且最难回退。

## 8. 自动生成的资产越来越多，靠什么管

Agent 能自动搭场景，确实会产出更多需要检查的资产。现在的承接方式：

- **保存创作约束** → `shot.lock`（九个维度，编进提示词 + 拦在 dispatch）、`asset.approve`（参考图绑实体）
- **执行局部修改** → 逐镜 `generation.submit`、`camera.nudge` 这类带单位的相对操作、`film.export {source:"auto"}` 只换动过的那一镜
- **检查结果** → `review.verify` 逐项对比，结论进 `shot.lastVerdict`
- **支持回退** → 每个 Action 进事件日志（source / actorId / before / after / forced），`project.undo` 与 `undo-to <eventId>`；切换工程前自动扣快照

四件事各自都有对应的 Action，所以人、CLI 和 Agent 用的是同一套——Agent 自动生成的资产，走的是和人一样的验收与回退路径。

## 9. 交互：该问的时候要问，而且要问得专业

参考 Meshy 那个「三视图转 3D」的对话——它的价值不在于执行，在于**先说出你没意识到的约束**：这张图是三视图合集、直接喂给拓扑会错乱；智能拓扑只出白模、PBR 要再走一次贴图。然后给选项、给推荐，等你拍板再动手。

planner 的输出协议因此加了两块：

```json
{"ask":[{"question":"…","why":"不问会怎样","options":[{"label":"…","detail":"这么选会发生什么","recommended":true}]}],
 "suggest":["做完这一步之后最可能的下一条指令","…"]}
```

规则写在系统提示词里：**只有当不同选择会导出明显不同的结果、而上下文判断不了时才问**；问就必须先说清看出了什么问题、不处理会怎样，再给 2–3 个带推荐的选项。能合理默认的一律不问，按默认做完把假设写进 notes。`ask` 非空时不执行任何改动。

实测（把角色三视图要求做成 3000 面 PBR 资产）：

> 我看到了两个阻塞点：三视图尚未进入工程资产清单，而且导演台不能直接完成 3000 面重拓扑与 PBR 烘焙。若直接继续，最多只能约束生成画面中的角色外观，不能得到可用于预演的真实 3D 主角模型。
>
> **你希望按哪条流程接入这张角色三视图？** 两条流程的结果不同：GLB 路线会真正替换主角白模；视觉参考路线只约束后续生成画面的角色一致性。
> - 提供外部制作好的 3000 面 PBR GLB **· 推荐** — 我会替换 hero 的代理体并保留现有位置、走位与全部镜头引用
> - 把三视图作为角色视觉参考 — 绑定并批准给 hero，用于后续镜头生成，场景内仍是白模
> - 暂时保留白模 — 继续用现有代理体完成机位和调度预演

**下一步建议也改成 planner 给的**。原来是写死的几句进度推断（「还没有 Take 就建议录 Take」）。现在由规划器根据这一步之后工程的真实状态给出可直接执行的指令，例如上面那轮之后给的是「切到 B 机查看构图」「把 B 机改成略微俯拍的 MCU」「预演镜头 02，循环播放」。规则推断保留为兜底——离线、用规则规划器、或模型没给建议时仍然有东西可点。

## 10. 从 Hyper3D 能借的

| 他们做的 | 对应到导演台 | 现在的状态 |
|---|---|---|
| **WorldGen**：一张场景图 → 自动识别主要物体 → 拆成可编辑/可替换/可交互的独立资产 | 一张参考图 → 白模场景（现在只能从文字建场） | **没做**。语义代理体系（`semanticType` / `proxy` / `dimensions`）本来就是为「可替换」准备的，缺的是图片→实体清单这一步 |
| **Mesh + 3DGS 混合表达**：要交互的物体是 Mesh，背景用 3DGS 保留环境信息 | 完全一致的取舍：主体用语义代理体（可摆位、可遮挡、可算轴线），背景交给生成模型 | 已经是这个分工，只是背景那半交给了 T2V 而不是 3DGS |
| **预测碰撞体、质量、摩擦等物理属性** | 实体现在只有几何与语义，没有物理属性 | **没做**。对预演的价值在于「站得住、撞得到、挡得住」，不是仿真 |
| **资产可替换** | `entity.replace-proxy`：换 GLB 不动 `semanticType` / `id` / `continuity` / `usedByShots` | **已有**，这正是上面那轮反问里第一个选项 |
| **Rodin MCP**：把 3D 生成作为 MCP 嵌进 Agent 工作流 | 把导演台本身做成 MCP server，让外部 Agent 驱动 | **没做，但很近**：`/api/capabilities` 已经能列出全部 Action 的参数与状态机许可，`/api/actions` 已经是统一入口，包一层 MCP 基本是格式转换 |

最值得先做的两件：**MCP 封装**（几乎是现成的，能让 Codex / GPT / Claude 直接驱动导演台）和**图片建场**（WorldGen 那条路，把「一张参考图」变成建场输入，比纯文字准得多）。物理属性对预演价值有限，放最后。

## 11. 长链的健壮性：失败要能接着跑，而不是从头再来

一条 60 秒的链要跑十分钟以上，中途一定会失败。所以链有了**段级账本**（`parts[]`：每段的状态、jobId、url、失败类型），失败分三类处理：

| 类型 | 判据 | 处理 |
|---|---|---|
| `transient` | 超时 / 网络 / 5xx / 限流 | 自动重试（默认 2 次） |
| `content` | 内容策略、版权、敏感词拦截 | **不重试** —— 同一条提示词重试多少次都会再被拦，只会烧钱。提示改写描述后 resume |
| `fatal` | 参数非法、供应商不认识 | 不重试，直接说清楚 |

`shot.chain --resume` 从第一个没完成的段接着跑，**已经出好的段原样沿用**（用的还是原来那个 url，不重新生成）。实测：5 段的链在第 3 段被内容策略拦下 → 前 2 段状态是 done → 改完提示词 resume → 沿用 2 段、只跑后 3 段 → 完成。

这一条直接对应上一节那个真实教训：city-edge 示例跑长链时第一段就被 `PolicyViolation` 拒了，而且是**出片之后才拦**。没有段级账本的话，那一条链所有已完成的段都白花。

## 12. 角色卡：脸、身、服装、声音是同一个人

参考资产过去是平铺的一堆图，模型收到时分不清哪张是脸、哪张是造型，只会平均一下。现在资产带 `role`：

`face 面部 / body 身形 / wardrobe 服装 / prop 物品 / style 风格 / voice 配音`

- `generation.reference {entityId, role}` 按 role 出不同的参考图：要脸就拍头肩特写、要服装就拍整套 head-to-toe —— 一张图管一件事，混在一张里两头都学不准。
- 提交生成时提示词里逐张说明：`[1] 主角 A — facial identity, match the face exactly; [2] 主角 A — clothing, color and fabric`，末尾加一句 `do not blend them together`。
- `context.character {id}` 返回整张卡：身份字段、按 role 分组的资产、缺哪几面（`missing`）、出现在哪些镜头。
- **配音是卡上的一格，但现在填不了**：两个网关都没有开 `/v1/audio/speech`（见 `docs/capability-test.md`）。数据模型已经留好（`mediaKind: "audio"`，不会混进画面参考），接一家 TTS 就能用。

## 13. 第一次打开：一句话到一条能播的片子

老的第一屏要求你已经知道「镜头 / 机位 / Take / 故事版」是什么，对没做过片子的人每个词都是门槛。现在空工程第一次打开是一个输入框加三句示例：

```
说一句你想要的片子
剩下的我来跑：搭场景、分镜头、出一条能播的白模成片。大约一两分钟，不花钱。
```

跑的时候三步旁白（搭场景 → 逐镜白模 → 拼片），每步都显示在做第几镜、叫什么名字——**跑长流程时沉默比慢更让人不安**。跑完直接播那条片子，然后才问要不要花钱出画面。

**默认只跑到白模**是有意的：白模不花钱、一两分钟出结果，让新用户先拿到一条真的能看的东西；真实生成计费，放在成片之后单独问一次，不替用户决定。

实测（"一条 15 秒的咖啡品牌短片：晨光里的一杯手冲…"）：52 秒建出 3 镜共 15 秒 → 16 秒录完 3 镜白模 → 拼成 14.9 秒成片，全程约 70 秒，零页面错误。

顺带修了一个会真实发生的故障：窗口被最小化或完全遮挡时浏览器停掉渲染循环，播放头不前进，录像器永远等不到出点。原来只报 `RECORD_TIMEOUT`，现在会说「录不到画面：录制期间窗口要保持可见」。
