# 产品技术边界

来自用户提供的技术选型及后续明确修订。约束针对本产品，不推广为所有项目的技术规则。

## Semi Design 与界面

- 使用 Semi Design / Semi UI 统一基础交互，查询当前安装版本的官方组件文档，不猜 API。
- 表单、弹窗、菜单、提示等优先使用现有组件；产品特有界面通过组合实现，不默认引入 Radix 或其他平行组件库。
- 使用 Semi 的主题及设计令牌，产品扩展遵循统一约定。优先公开 API 和扩展点，避免覆盖内部 DOM 或私有类名。
- 不为每个 Semi 组件机械包装；仅为重复业务语义、交互规则或明确替换边界封装。
- Motion 按需用于自定义动画，避免与内置动画重复控制同一状态。
- 实测键盘、焦点、表单反馈、空态、失败、主题及相关响应式状态；不能假定组件库已保证组合后的行为。
- 浮层测试覆盖实际 Portal 内容，使用角色和可访问名称等用户可见语义定位，不绑定内部类名。
- 官方入口：[Semi Design](https://semi.design/en-US)。

## 组件抽离与 Tailwind CSS

- 每个独立组件使用单独 `.tsx` 文件，一个文件只承担一个主要组件职责。页面负责组合，子区域、列表项、弹窗等有明确职责的组件就近抽离，不在父文件堆叠多个组件定义。
- 不在组件渲染函数内部定义子组件；不要用 renderXxx 辅助函数、压缩 JSX 或搬到非 TSX 文件绕过组件抽离和行数上限。
- 组件 TSX 文件超过 300 行提醒、超过 500 行报错，每个函数含 JSX 最多 10 行，具体计数遵循主文件。用可命名的组件边界拆分，不创建无语义转发组件。
- 子组件通过明确 props 获得需要的数据与回调；共享状态由合适的父层或 Zustand store 维护，不因拆文件复制状态或把完整 store 传遍组件树。
- 纯领域计算放普通 TypeScript 模块，React 生命周期组合放 Hook；不将一整个业务流程藏进 Hook 以满足组件行数限制。
- 样式统一使用 Tailwind CSS 最新稳定版。新接入或升级时查询官方发布记录及包仓库稳定版本，将 `tailwindcss` 及配套插件的具体版本精确写入 package.json 并提交锁文件；不使用预发布版本、范围前缀或让每次构建浮动追踪 latest。
- 当前参考官方 v4 文档；实施时核实最新稳定版本对应的接入方式与兼容要求。现有项目升级需检查迁移指南、Electron 内嵌 Chromium、Vite 和插件兼容性，不仅替换版本号。
- Vite 项目优先使用官方 `@tailwindcss/vite` 插件，匹配 `tailwindcss` 版本，在应用普通 CSS 入口接入。v4 默认采用 `@import "tailwindcss"`；不套用旧版初始化及配置方式。
- Tailwind 负责产品布局和自定义外观，Semi 继续负责基础交互组件。通过统一的语义令牌、CSS 变量及必要的 Tailwind 主题映射复用 Semi 主题，不维护互相冲突的颜色和暗色模式体系。
- 检查 Preflight、CSS 层顺序及第三方样式优先级对 Semi、React Flow 和预览内容的影响。确有冲突时通过官方导入方式按需省略 Preflight 或明确层级处理，不依靠大量 !important 和覆盖私有选择器。
- 优先组合实用类及响应式、状态变体。类名必须以源码中可识别的完整形式出现；动态选项用有限的完整类名映射，不拼接 `bg-${color}-500` 等片段。
- 运行时坐标、尺寸等连续值使用必要的内联样式或 CSS 自定义属性，不生成无限类名。避免到处散落任意值；重复语义进入统一令牌或明确组件。
- 条件类名优先沿用现有工具；需要复杂合并时选与当前 Tailwind 版本兼容的成熟库，不手写冲突解析器，也不为简单 className 叠加通用样式框架。
- 类名较长时按组件职责和可读性整理，不为凑函数 10 行压缩 JSX，也不将全部样式搬进大段 @apply；独立组件及 300 行提醒 / 500 行报错规则仍生效。
- 自定义 CSS 仅用于 Tailwind 难以清晰表达的实际需求，使用浅层、明确作用域的选择器。
- Tailwind 样式入口使用官方支持的处理链，不额外叠加无必要的预处理器；保留第三方库实际需要的构建能力。
- Vitest / React Testing Library 按行为定位，不断言完整 utility 类串。真实主题、响应式和 Preflight 影响另行验证；生产构建检查条件类名被正确生成，不能只依赖开发环境外观。
- 官方参考：[Vite 接入](https://tailwindcss.com/docs/installation/using-vite)、[兼容性](https://tailwindcss.com/docs/compatibility)、[类名检测](https://tailwindcss.com/docs/detecting-classes-in-source-files)、[Preflight](https://tailwindcss.com/docs/preflight)、[发布记录](https://github.com/tailwindlabs/tailwindcss/releases)。

## useEffect：单一同步职责

- 先判断是否需要 Effect。渲染派生数据使用纯计算或 selector，昂贵计算有依据时再缓存；点击、提交、导出等用户动作在事件处理函数中调用应用用例，不先设标记再靠 Effect 执行。
- 一个 Effect 表达一个独立的外部同步过程，例如管理某项订阅、连接或媒体资源。按实际依赖和生命周期拆分，不将加载、监听、状态重置、计费及通知塞进一个 Effect。
- 同一资源的建立与清理保留在同一 Effect 生命周期中；具有独立依赖、可单独停止的过程才分开。不要按语句数量拆成相互依赖执行顺序的多个 Effect。
- Effect 回调、清理函数和提取的函数都遵守最多 10 行。复杂度通过明确的纯函数、资源适配器或专用 Hook 降低，不把复杂 Effect 原样搬进一个大函数，也不压行凑数。
- 提取的 Hook 以业务同步职责命名，暴露明确输入和结果；不创建 useMount、useEffectOnce 等通用包装来隐藏依赖或规避重复执行。
- 保持 `react-hooks/rules-of-hooks` 和 `react-hooks/exhaustive-deps` 检查。依赖反映真实使用的响应式值，不能用空数组、禁用规则、JSON.stringify 或深比较 Hook 掩盖不正确的依赖设计。
- 对象和函数引用导致无谓重跑时，先调整创建位置、职责及输入，不默认叠加 useMemo / useCallback，也不用 ref 隐藏本应响应的值。
- 有监听、定时器、连接或资源就明确清理，依赖变化与卸载时释放旧资源。不得将 Effect 回调本身标记为 async；异步工作由明确函数执行并处理错误。
- 异步请求按实际能力取消或忽略过期结果，避免旧项目、旧请求在新状态中落地；忽略结果不等于取消远端副作用。需要缓存、去重或复杂请求管理时优先复用已有数据层，不在 Effect 中自建请求框架。
- 不通过 Effect A 更新状态触发 Effect B 再触发 Effect C 编排业务；用明确的事件调用、应用用例或状态归约表达流程。Zustand 与 React 状态不通过双向 Effect 复制同步。
- 需要 Effect 时，应能承受开发环境 Strict Mode 的 setup → cleanup → setup 检查；不使用“只执行一次”的 ref 标记或关闭 Strict Mode 掩盖缺少清理、重复调用等问题。
- 相关 Vitest / React Testing Library 用例覆盖依赖变化、卸载、重复建立与清理、异步过期结果及必要错误反馈；验证实际行为，不断言组件内部有几个 Effect。
- 官方参考：[You Might Not Need an Effect](https://react.dev/learn/you-might-not-need-an-effect)、[Removing Effect Dependencies](https://react.dev/learn/removing-effect-dependencies)。

## Zustand：简洁的客户端状态

- 客户端共享 store 统一使用 Zustand。组件独有的展开、输入等状态优先留在 React 本地；不把所有状态提升为全局 store。
- 默认使用直接的 state + actions + selectors。纯 React 共享界面状态可直接用 `create`；需要独立实例、依赖注入或非 React 使用时，用 `zustand/vanilla` 的 `createStore`，界面通过 `useStore` 接入。按需求选择，不机械维护两套。
- 一个 store 围绕一个业务能力或一致的生命周期组织，不堆成万能全局 store，也不按字段机械拆分。默认先保持一个清晰的小文件，实际复杂后再拆。
- 不默认引入 slices、Immer、persist、自动 selector 生成、工厂套工厂或通用 BaseStore；只有明确解决当前问题时才增加。Devtools 按调试需要启用，避免暴露敏感状态。
- 简单 action 直接完成不可变更新，依赖旧状态时使用函数式更新。优先扁平结构，不为浅层更新引入额外依赖。
- 组件通过 selector 订阅所需字段，不默认订阅整个 store。优先单字段 selector；组合输出需要遵循安装版本对引用稳定性的要求，必要时使用 `useShallow`，不盲目叠加 memoization。
- 派生值优先在 selector 或纯函数中计算，不重复存储可廉价计算的状态并维护同步。
- Zustand 管理界面状态和领域结果的展示投影；SQLite 事件日志、检查点及 reducer 继续作为持久化领域状态的权威来源。禁止另建同一业务事实的可独立写入副本。
- 持久化业务修改调用应用用例，再依据明确的结果或事件更新投影；不要用 store 订阅偷偷触发写库、计费或媒体生成，也不要让两个 store 相互订阅维持业务流程。
- 领域规则不导入 Zustand，不接收完整 StoreApi。简单异步 action 可调用明确的应用接口，复杂流程仍由应用层组织，store 只协调界面状态。
- 明确应用、窗口和项目作用域。项目状态需要独立实例或明确重置；异步结果按项目/请求归属处理，防止旧任务更新新项目。模块级 store 仅用于作用域确实匹配的共享界面状态。
- 不默认将整个 store 持久化。确需保存偏好时，只白名单保存必要字段，定义版本和迁移；不保存密钥、运行句柄或重复保存领域数据库内容。
- Vitest 验证 action 的结果、派生状态、实例隔离/重置和相关异步过期结果；测试使用独立实例或可靠重置并释放订阅，不因 Zustand 共享状态相互污染。
- 官方参考：[Zustand README](https://github.com/pmndrs/zustand#readme)。以安装版本对应文档为准。

## React Flow 画布

- 复用节点交互、连线、平移、缩放、小地图；领域模块决定节点意义与执行规则，节点组件不承载流程引擎。
- 不直接以 React Flow 内部对象作为稳定存储协议。临时悬停、框选、拖动状态与需保存的数据分开；布局保存按产品约定。
- 性能问题先测渲染、订阅、连线与布局；约 500 节点是评估触发点，不是库的固定上限或自动迁移理由。

## 事件状态核心

- 用 SQLite / better-sqlite3 存储事件日志，TypeScript reducer 自建状态演进，Zod 校验边界。
- 持久化产品操作遵循事件与检查点模型，临时 UI 状态不必全部入日志。
- reducer 保持确定，不访问网络、时钟或随机数；时间、标识和外部结果作为显式数据输入。
- 副作用与归约分离；历史回放不得再次触发付费、文件写入和媒体处理。
- 事件结构变更说明旧数据读取或迁移策略。保护检查点与回放语义，不把“永不重新评估”理解为永久锁死存储实现。

## 智能体与操作集

- 复用 Pi agent core / pi-ai 的循环、流式工具调用与模型提供方抽象，实际包名及 API 以依赖和官方文档为准。
- 自建上下文和技能内容；不为修改提示词或新增工具另建 agent framework。
- UI、智能体和 MCP 复用领域操作，各入口按需限制权限。工具必须验证参数和业务规则，不绕过操作层直接改库。
- 更换 SDK 需相同评测集证据，并评估成本及供应商依赖。

## 小型 DAG 引擎

- 自建当前领域需要的 TypeScript DAG 编排语义、缓存规则和预算守卫；图算法、哈希、并发控制等通用机制优先复用平台或成熟库。不提前实现通用工作流平台或分布式调度。
- 明确输入、输出、依赖、失败与取消；执行前检测循环和缺失输入。
- 缓存键覆盖影响结果的输入、配置、实现和资源版本；可变外部资源有明确失效策略。失败、取消和不完整输出不是成功缓存。
- 在产生费用的边界检查预算，重试也受预算控制。
- 可借鉴 ComfyUI 语义，不直接复制或链接其 GPL 代码实现本地核心。桥接属于明确需求，接入时单独核查许可，不假定进程隔离自动解决许可问题。

## 媒体与预演

- 复用 ffmpeg、Web Audio 和 WebCodecs，按目标平台核实实际能力；按任务区分实时预览和离线处理。
- 源文件默认保留，输出避免覆盖；任务具备错误、取消和释放语义。发布时核查 ffmpeg 的实际构建参数和组件，不能只凭名称判定许可。
- three.js 负责渲染，自建场景 DSL、校验器与探测器；DSL 是可验证数据，不是可执行的任意脚本。
- 场景与决策、事件和检查点保持关联。可重复预演显式输入时间、种子和资源版本，不承诺跨设备逐像素一致。
- 本地渲染仍消耗算力、能耗与维护成本，不能把原截图的“边际成本为零”解释为无资源成本。

## 网关与 MCP

- 沿用 Mossland 的账号、额度和网关，在现有边界扩展价目、路由及适配器；不在桌面复制独立计费体系或供应商密钥体系。
- 用户自带密钥是明确产品扩展，不因阶段备注提前实现。
- MCP 作为操作集的薄适配层，负责协议、入口校验和转换，业务逻辑由应用和测试共用。

## 重新评估与缺失信息

普通开发不重开整套选型。只有证据或明确需求触发评估：

| 层级 | 触发条件 |
| --- | --- |
| Electron | 包体或内存已影响目标用户；新增 Rust 工程师本身不足以迁移 |
| 界面栈 | 默认 P0–P2 保持稳定；明确新要求时再评估 |
| 画布 | 目标规模接近/超过约 500 节点或更早出现实测瓶颈 |
| 状态核心 | 保留产品语义，因可靠性或迁移需要调整实现 |
| 智能体 | 等价评测证明更优且成本和依赖可接受 |
| DAG | 继续小型核心；有明确需求再桥接 ComfyUI |
| 媒体 | 逐帧精确剪辑等当前管线无法满足的需求 |
| 预演 | 替代方案满足控制、可重复性和总体成本要求 |
| 网关 | 明确需要用户自带密钥 |
| MCP | 产品互操作标准确实改变 |

触发评估不等于授权迁移；说明收益、代价、兼容和回退。截图中的“承诺 2”“07.14”和 P0–P2 未展开，不自行补写含义或时间表；仅在当前任务依赖这些定义时查产品文档或澄清。
