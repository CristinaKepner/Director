# 持续维护项目 AGENTS.md

目标：让后续开发者和编码代理进入仓库后，知道从哪里开始、如何运行验证、哪些边界不能破坏，以及到哪里查业务事实。

## 读取与维护范围

- 开始修改前读取适用的 AGENTS.md，包括上级目录与目标目录作用域内的规则；已有约定优先理解，不未经检查套用模板。
- 初始化项目时建立或完善根 AGENTS.md。修改目录组织、开发命令、工具链、编码规范、架构边界或发现经验证的长期注意事项时，同步更新对应规则。
- 已存在时做最小增量修改，保留用户维护内容及无关规则，不整份覆盖、不改变文件名、不另建竞争性入口。
- 只在子目录确有不同环境、命令或边界时增加局部 AGENTS.md，说明适用范围；共享规则留在根文件，不复制整份。
- 只维护当前目标仓库及任务相关作用域，不据此修改用户全局配置或其他仓库。
- 指引与当前明确要求冲突时说明差异并按指令优先级处理；不通过修改 AGENTS.md 消除尚未解决的冲突，不自行放宽约束或创造审批流程。

## 应沉淀的内容

保持简洁、具体、可执行，优先记录会影响后续决策的项目事实：

- **项目与目录地图**：主要应用、入口、功能模块、宿主/渲染/共享代码和相关配置位置。
- **环境与运行命令**：包管理器、运行时及锁文件，package.json 依赖精确版本规则和项目级保存配置，安装、开发、类型检查、lint、Vitest、构建和实际 Electron 验证入口；配置项和示例文件的位置。
- **架构边界**：进程职责、依赖方向、服务与状态归属、IPC 边界及公开模块入口，链接详细架构文档。
- **实际技术约定**：Semi、Tailwind、Zustand、严格 TypeScript、Vite、Vitest，以及组件抽离、TSX 超过 300 行提醒/超过 500 行报错、函数最多 10 行和单一职责 Effect 等在本仓库的实现位置。
- **验证要求**：默认 TDD 红—绿—重构流程，哪些改动需要哪类检查，测试文件组织，关键规则的单元测试要求、实际覆盖率命令与已有门槛，以及真实 Electron/发布包与模拟测试的区别。不得把尚未配置的覆盖率检查写成已实施。
- **资料导航**：业务文档索引、数据契约、迁移说明及关键测试入口，使用仓库相对链接。
- **维护注意事项**：生成文件、原生依赖、打包资源、平台限制，以及可重复的问题触发条件和已经验证的解决方式。

不要强制固定模板章节或字数。仓库规模小就保持短文，细节放对应文档后链接。

## 事实准确与可复用

- 从 package.json、锁文件、配置和真实目录验证命令与路径，不凭惯例写入不存在的 `test`、`typecheck` 或 `build` 脚本。
- 可安全验证的命令实际执行；未执行或被环境阻断时明确说明，不标记为已验证。不要为验证文档而运行发布、生产写入或真实付费操作。
- 区分“仓库已经实施的约定”和“计划接入的要求”，不把已写进 Skill 的规则伪装为仓库已经配置完毕。
- 版本要求指向仓库版本文件和锁文件；时间敏感的快照注明核对依据，不把“latest”永久写成某个未经维护的版本号。
- 不记录凭据、个人机器绝对路径、临时端口/PID、一次性任务状态、未证实推测或聊天转录。
- 稳定经验要说明适用条件，不把某次故障的修复命令推广成每次必须执行的清理步骤。
- AGENTS.md 是项目操作指引：不要用它堆放完整业务规则、完整 Skill、第三方手册或发布日志。

## 与业务文档配合

- AGENTS.md 回答“怎样在这个项目中正确工作”；`docs/business/` 或仓库已有位置回答“产品为什么这样运行、规则是什么”。
- AGENTS.md 提供必须查阅的业务索引和迁移资料入口；业务文档链接具体实现与测试，避免重复维护。
- 更新业务规则通常只修改对应业务文档；只有导航、开发方式或稳定约定变化时才修改 AGENTS.md。
- 新增模块时确保后续人员能找到入口及验证命令；迁移后移除过时路径和命令，必要历史信息保留在迁移说明中。

## 完成前检查

- 指令是否具体到实际文件、入口或命令，并且作用域明确？
- 链接和命令是否真实，是否与当前配置一致？
- 是否保留无关用户内容，避免根目录和子目录规则重复或冲突？
- 是否把业务详情放回对应文档，避免入口过长？
- 是否把计划、临时状态和未经验证结论误写成长期事实？

交付时给出更新位置及原因；仅在有相关变化时更新，不为每个任务机械追加一段记录。
